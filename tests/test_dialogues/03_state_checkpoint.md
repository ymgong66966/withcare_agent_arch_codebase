# Test 03: State Checkpoint — Survive Pod Restart

**User ID:** `test-alice` (continue from Test 02)
**Purpose:** Simulate a pod restart by hitting /reset, then verify state is fully restored from DDB.

---

## Step 1 — Note the current state

Before resetting, look at the debug panel and note:
- `conversation_id` (the first 8 chars shown in the UI header)
- `active_request.request_id`
- `active_request.status` (should be `executed` from Test 02)
- `current_agent`
- `total_requests`

Write these down — you'll verify they come back after reset.

---

## Step 2 — Reset (simulate pod restart)

Click the **Reset** button in the chat UI (or send `POST /reset` with the conversation_id).

**EXPECT:**
- Chat history clears in the UI
- The "New conversation" label appears in the header
- The in-memory `_conversations` cache for this session is deleted

**What this simulates:** A pod restart. The in-memory state is gone. Only DDB persists.

---

## Step 3 — Send a new message with the SAME user_id

Important: Make sure `test-alice` is still in the User ID input field. The conversation_id will be new (generated by the server).

**YOU:**
```
Hi, I was looking for a caregiver for my mom earlier. Can we continue?
```

**EXPECT:**
- **Reply:** The agent should have context about Alice. Two possible behaviors:
  - (a) **Cross-session resume**: If the collection plan prompt matches the new request to the old "Find In-Home Caregiver" request (status: executed), it may reference the previous search or acknowledge the prior work.
  - (b) **Fresh request with facts**: Even if it creates a new request, the stored facts from Test 02 (mom's location in South Loop, budget $3000, Mandarin preference, mild dementia) should be available via `known_facts` and the agent should NOT re-ask for information it already knows.
- **Debug panel:**
  - This is a NEW `conversation_id` (different from the old one)
  - `current_agent`: Likely `info_collection`
  - If cross-session resume worked:
    - Look for "resumed_cross_session" in `stage_detail`
    - Or the reply explicitly mentioning "I found your previous request"
  - If fresh request:
    - `active_request.info_collection.summary` may already contain facts from the stored profile
    - Questions should NOT ask for location, budget, or language (already known)

**What this tests:**
1. **Checkpoint restore**: The routing state (current_agent, needs_human, conversation_stage) was checkpointed to DDB and restored
2. **Request reload**: The executed caregiver request was reloaded from `UserRequestTable`
3. **Fact persistence**: Facts written during Test 02 are available via `get_context_bundle()`
4. **Cross-session resume**: The LLM matching in the collection plan prompt may detect the old request and resume from its collected info

---

## Step 4 — Verify facts are pre-filled

**YOU:**
```
Yes, I want to continue the caregiver search.
```

**EXPECT:**
- **Reply:** The agent should reference previously collected info. Look for mentions of:
  - South Loop / Chicago (location)
  - $3000 budget
  - Mandarin / Chinese language
  - Mild dementia
  - Monday-Friday, 6 hours
- If the agent asks questions, they should be ONLY about what's NOT already known (e.g., "Would you like to adjust any of the previous criteria?" or "Is there anything new to add?")
- **Debug panel:**
  - `info_collection.summary` should contain the previously collected details
  - `known_facts` section in memory_context should show stored facts

**What this tests:** The "don't re-ask what's already known" behavior. Facts persisted in `UserFactTable` feed into the collection plan via `filter_questions_with_known_facts()`.

---

## Success Criteria

This test passes if:
1. After reset, the agent still knows who Alice is and what she was working on
2. Previously collected facts (location, budget, language, condition) are NOT re-asked
3. The debug panel shows state was restored (routing, request_manager populated)
4. The conversation flows naturally despite the "pod restart"

## If It Fails

- **No facts restored**: Check if `WithCare_UserFactTable` has entries for `USER#test-alice`. If empty, fact binding in Test 02 didn't write to DDB (check DDB connectivity).
- **No request restored**: Check if `WithCare_UserRequestTable` has entries for `USER#test-alice`. If empty, the `_append_request_ddb_sync` calls didn't persist.
- **Checkpoint not found**: Check `WithCare_UserConversationTable` for `CONV#{old_conv_id}`, `SK=CHECKPOINT#latest`. If missing, the checkpoint write in `_run_turn` failed.
- **New conv_id means no checkpoint**: The checkpoint is per conversation_id. Since we have a NEW conversation_id after reset, the checkpoint from the old conversation won't be found. However, facts and requests are scoped by **user_id**, so those should still be available via `query_recent()` and `get_context_bundle()`.
